Catalogue N° I MMXXVI · April

The WonderLens Pipeline, & its seven stations.

A reference catalogue — prepared for the intern rotation — of the upstream inputs, the authoring layer, and the runtime that together transform a single entity into a playable game.

The pipeline is three things pretending to be one. Upstream, a small set of scripts produces structured data — a list of entities, their IB assignments, age-tier scaffolding. In the middle, an authoring layer turns that data, together with the game design playbook, into a design. Downstream, a runtime takes the resulting recipe and plays it as a game with sound, animation, and photo capture.

The middle is where interns do their work. The design studio in this repository is one reference implementation of that middle; you may use it, fork it, or write your own from scratch. Whatever you build must read the upstream YAMLs and emit recipes the runtime loader accepts. Everything else — language, framework, interface — is your choice. The playbook, not the code, is the final arbiter.

Plate II

The catalogue

N° IBand I · Upstream

Entity List

The seed of the pipeline. Every downstream artifact begins here.

File
scripts/entity_list_generator.py
Input
Seed prompts and domain categories — animals, objects, places, foods.
Output
A CSV of entities, one row each, with name, domain, and keywords.
Verify
Pick three rows across different domains. The keywords should feel evocative and age-appropriate for the target tier.
N° IIBand I · Upstream

IB Theme Batch

The authoritative IB assignment for each entity.

File
scripts/ib_theme_batch_generator.py
Input
The entity CSV together with the PYP transdisciplinary theme catalogue.
Output
A YAML mapping each entity to an IB theme and one or more key concepts.
Verify
Take the same three entities from N° I. The theme assigned should be a credible choice — the one a seasoned PYP teacher would pick.
Note
This file is meant to be read structurally by the authoring layer, not paraphrased in a prompt.
N° IIIBand I · Upstream

Tier Guidance

Age-appropriate scaffolding for each tier: T0, T1, T2.

File
scripts/exploration_tier_generator.py
Output
A YAML with per-entity, per-tier scaffolding: vocabulary, sentence complexity, cognitive-load cues.
Verify
Compare T0 and T2 for a single entity. T0 should be shorter, simpler, more concrete.
Note
This is how age-appropriateness becomes deterministic. Feed it to the authoring layer as structure, not prose.

Playbook-driven. One station, many valid implementations.

Plate III

The two challenges

Challenge A · Between Bands I & II

Consume the YAMLs. Do not re-invent them.

band i's output → your authoring layer

The upstream scripts exist so that IB themes and tier scaffolding are deterministic. Any authoring layer that re-guesses them inside an LLM prompt throws that determinism away. Read the files as structured input, cite the exact theme and key concept assigned, and let the rubric verify the output matches its source.

  • The assigned ib_theme and ib_key_concept should be deterministic, not sampled.
  • Tier scaffolding should not drift run-to-run for a single entity.
  • The list of concepts_earned should be pre-computed, not invented at export time.
  • If your layer cannot cite a source YAML for a given design, the game was already lost upstream.
Challenge B · Between Bands II & III

Emit a valid recipe — first try.

your authoring layer → refs/backend/recipe_loader.py

The runtime has a strict Pydantic schema. Any authoring layer that emits prose and hopes a second model will turn it into widgets, SFX cues, and tone markers is building on sand. Produce a recipe that the loader accepts the moment it is written — with every asset identifier already resolved — and no bridge step will be needed.

  • YAML frontmatter with activity_type, metadata, ib_theme, concepts_earned.
  • Structured screen_frames with widget, widget_params, animation, trigger, sfx_cue.
  • Tone markers — [warm], [excited] — on every voice line.
  • A celebration_frame where the playbook calls for one.
  • For Category 5: collection_catalog, collection_count, photo_features.
Plate IV

Five exercises

Five hands-on exercises, done in order. Each consumes the previous one's output. By the end of Exercise V the intern will have built a complete game from scratch, validated it against the runtime, and know exactly where to extend it next.

I

Generate the inputs

Upstream data is deterministic. Start there.
Open
scripts/entity_list_generator.py, ib_theme_batch_generator.py, exploration_tier_generator.py
Run
All three in sequence.
Inspect
Pick three entities from the CSV. Trace each through both output YAMLs. Do the IB theme and tier scaffolding make sense?
Ask yourself
If your authoring layer could read these files directly, what would it stop guessing?
II

Read the playbook

The source of truth. Read it once, end to end.
Open
docs/game_design_playbook.md
Focus
The ten-dimension rubric, the six experience pillars, the twelve game styles, the phase structure, the bracket tone markers.
Ask yourself
If you were scoring a design without looking at the code, which rubric dimensions would be hardest to grade?
III

Read the runtime schema

The target format. Strict, unambiguous, unforgiving.
Open
refs/backend/schemas/recipe.py, refs/backend/schemas/visual_composition.py
Exercise
Walk every class. List every required field. Note the cat 1 / cat 5 split. Find every field that references an asset identifier.
Ask yourself
Which fields can be authored directly by an LLM, and which need deterministic sources from Band I?
IV

Inspect a reference game

See what 'good' looks like on both ends.
Open
refs/backend/games/polka_dot_patrol.md, or any reference game.
Exercise
Read the frontmatter slowly. Map each field back to the playbook and forward to the runtime schema. Note which fields are deterministic and which are authored.
Ask yourself
How much of the frontmatter could be filled in mechanically from Band I alone? How much requires real authoring judgement?
V
Capstone

Build a complete game

From a fresh entity to a loadable recipe. The whole arc.
Pick
A new entity not yet in the CSV. Something specific and visual.
Prepare
Run the Band I scripts on it (or do the equivalent by hand). Produce its IB assignment and tier scaffolding.
Author
Build the design. Use the reference implementation in this repository, or write your own from scratch. Follow the playbook. Pick one pillar, one game style, one tier.
Emit
A recipe the loader accepts the first time. No post-processing. No bridge script.
Validate
Load it, start the server, confirm the recipe appears at the endpoint without error.
Extend
Once it loads cleanly, add a round, swap an SFX cue, change the celebration frame. Confirm each change still loads.
Plate V

Recipe reference

A checklist for Challenge B, verified against the runtime schema.
Field Required Note
activity_type must The runtime's lookup key. Derived from entity and game style.
metadata.ib_theme must Read from the IB theme YAML. Do not re-invent in a prompt.
metadata.ib_key_concept must From the same source. A single concept, not a menu.
metadata.concepts_earned must Pre-computed from the rubric and playbook at authoring time.
metadata.tier must T0, T1, or T2, paired with the tier guidance YAML.
metadata.round_count must Must match the rounds authored in the voice script.
voice_script.hook_line must The opening line, carrying a hook tone marker.
voice_script.rounds[].tone_marker must Square-bracket tone per round — [warm], [curious], [excited].
voice_script.synthesis_speech cat 5 Required for collection-based styles.
voice_script.closing_line must With its closing tone marker.
screen_frames[].widget must A named widget identifier — photo_display, counter, badge — known to the frontend.
screen_frames[].widget_params must Parameters specific to the chosen widget. Type-checked at load.
screen_frames[].animation must A named animation — sparkle_highlight, fade_in — known to the runtime.
screen_frames[].sfx_cue must A named SFX identifier, resolved at runtime to an audio file.
screen_frames[].trigger must When the frame fires — round start, correct answer, closing, and so on.
celebration_frame optional A final screen on completion. Most playbook designs should have one.
collection_catalog cat 5 Correct items and distractors, with identifiers and match hints.
collection_count cat 5 How many items must be collected before synthesis.
photo_features cat 5 Hints for vision-based validation of captured photos.
