The WonderLens Pipeline

An intern walkthrough, from entity list to runnable game.

Prepared for the intern rotation, April 2026.
Abstract The WonderLens system spans three bands: a set of upstream Python scripts that produce structured data, an authoring layer that turns that data into a game design against the playbook, and a runtime that plays the resulting recipe. This note surveys the five stations an intern will touch, names the two implementation challenges that sit between the bands, and proposes five exercises for new interns. The design studio in this repository is cited only as one reference implementation; the playbook is the source of truth, and any authoring layer that reads the upstream YAMLs and emits recipes matching the contract in §5 is a valid one. The runtime itself is out of scope — it is a separate service, maintained by another team, that an intern's authoring layer hands recipes off to.

1. Overview

The pipeline has three bands and five stations that an intern will touch. Data flows downstream only. Each band is simple in isolation; the interesting work is in the two seams between bands, where interns will spend most of their time.

2. The five stations

The stations are numbered in order of data flow, not in order of importance. Station 4 is where an intern's work will live; the upstream scripts are fixed, and the runtime on the far side of station 5 is maintained by another team and is out of scope.

2.1 Entity list · n°1

Band I — upstream data
File
scripts/entity_list_generator.py
Output
entities.csv — one row per entity with name, domain, and keywords.
Verify
Pick three rows across different domains; the keywords should feel evocative and age-appropriate.

2.2 IB theme batch · n°2

Band I — upstream data
File
scripts/ib_theme_batch_generator.py
Input
The entity CSV plus the PYP transdisciplinary theme catalogue.
Output
entity_ib_map.yaml — per entity: an IB theme and one or more key concepts.
Verify
For the same three entities, is each assigned theme a credible choice?
Note
This is the authoritative IB assignment. It is meant to be read structurally by the authoring layer.

2.3 Tier guidance · n°3

Band I — upstream data
File
scripts/exploration_tier_generator.py
Output
tier_guidance.yaml — per-entity, per-tier scaffolding.
Verify
Compare T0 and T2 scaffolding for one entity. T0 should be simpler and more concrete.

2.4 Authoring layer · n°4

Band II — the intern's work lives here
Source of truth
docs/game_design_playbook.md
Reference implementation
src/lib/pipeline.ts, prompts/generate.ts, design-schema.ts — one way to do it, not the only way.
Must consume
The YAMLs from 2.2 and 2.3 as structured input (Challenge A).
Must emit
A recipe matching the contract in §5 (Challenge B).
Free to choose
Language, framework, storage, interface. A web app, a CLI, a Notion plugin, a Jupyter notebook, a bash pipeline — all valid.
Both challenges meet here. The implementation stands or falls on how cleanly it crosses the two boundaries on either side of this station.

2.5 Recipe handoff · n°5

Band III — recipe handoff (runtime is out of scope)
What it is
The handoff point between the authoring layer and the runtime. An intern's work ends here: once a recipe matches the contract in §5, the runtime takes over.
Contract
§5 of this document is the authoritative interface. Any recipe that satisfies it will run.
Out of scope
The runtime itself — the loader, the server, the frontend — is maintained by a separate team. Interns do not read or modify its code.
Validation
The runtime team provides a contract validator. Pass your recipe through it; if it accepts, the recipe ships.

3. The two challenges

Any authoring layer, not just this repository's, must solve the two challenges below. They are not implementation choices; they are the definition of a correct authoring layer.

3.1 Challenge A · Consume the YAMLs

The upstream scripts exist so that IB themes and tier scaffolding are deterministic. An authoring layer that re-guesses them inside an LLM prompt throws that determinism away. The layer must read entity_ib_map.yaml and tier_guidance.yaml as structured input and cite the exact theme and key concept assigned.

  • The assigned ib_theme and ib_key_concept should be deterministic, not sampled.
  • Tier scaffolding should not drift run-to-run for a single entity.
  • concepts_earned should be pre-computed, not invented at export time.
  • If the layer cannot cite a source YAML for a given design, the game was lost upstream.

3.2 Challenge B · Emit a valid recipe

The recipe contract in §5 is strict. An authoring layer that emits prose and relies on a second LLM pass to turn it into widgets, SFX cues, and tone markers is building on sand. The layer must produce a recipe the contract validator accepts on the first try, with every asset identifier already resolved. No bridge script. No second model. No prayer.

  • YAML frontmatter with activity_type, metadata, ib_theme, concepts_earned.
  • Structured screen_frames with widget, widget_params, animation, trigger, sfx_cue.
  • Bracket tone markers ([warm], [excited]) on every voice line.
  • A celebration_frame where the playbook calls for one.
  • For Category 5: collection_catalog, collection_count, photo_features.

4. Five exercises

Do them in order. Each consumes the previous one's output. By the end of Exercise 5, the intern will have built a complete game from scratch against the playbook, validated it against the runtime loader, and know exactly where to extend it next.

4.1 Exercise 1 · Generate the inputs

Open
scripts/entity_list_generator.py, ib_theme_batch_generator.py, exploration_tier_generator.py
Run
All three in sequence.
Inspect
Pick three entities from the CSV. Trace each through both output YAMLs. Do the theme and tier make sense?
Question
If your authoring layer could read these files directly, what would it stop guessing?

4.2 Exercise 2 · Read the playbook

Open
docs/game_design_playbook.md
Focus
The 10-dimension rubric, the six pillars, the twelve game styles, the phase structure, the bracket tone markers.
Question
If you were scoring a design without looking at code, which rubric dimensions would be hardest to grade?

4.3 Exercise 3 · Read the recipe contract

Open
§5 of this document.
Exercise
Walk every required field. Note the cat 1 / cat 5 split. Find every field that references an asset ID.
Question
Which fields can be authored directly by an LLM, and which need deterministic sources from Band I?

4.4 Exercise 4 · Inspect a reference game

Open
A reference recipe file provided by the runtime team (for example, polka_dot_patrol.md).
Exercise
Read the frontmatter slowly. Map each field back to the playbook and forward to the recipe contract in §5.
Question
How much of the frontmatter could be filled in mechanically from Band I alone?

4.5 Exercise 5 · Build a complete game · capstone

Pick
A new entity that isn't yet in the CSV. Something specific and visual.
Prepare
Run the Band I scripts on it (or do the equivalent by hand). Produce its IB assignment and tier scaffolding.
Author
Build the design. Use the reference implementation in this repo, or write your own from scratch. Follow the playbook. Pick one pillar, one game style, one tier.
Emit
A recipe matching the contract in §5, on the first try. No post-processing. No bridge script.
Validate
Pass your recipe through the contract validator provided by the runtime team. Confirm it is accepted without errors.
Extend
Once it validates cleanly, add a round, swap an SFX cue, change the celebration frame. Re-validate after each change.

5. Recipe contract

The fields below are the authoritative interface between the authoring layer and the runtime. Any recipe an intern produces must satisfy this contract; any recipe that does will run. Use it as a checklist for Challenge B.

Field Required Note
activity_type must Runtime lookup key. Derived from entity and game style.
metadata.ib_theme must From entity_ib_map.yaml. Do not re-invent in a prompt.
metadata.ib_key_concept must Same source. A single concept, not a menu.
metadata.concepts_earned must Pre-computed from the rubric and playbook at authoring time.
metadata.tier must T0 / T1 / T2, paired with tier_guidance.yaml.
metadata.round_count must Integer. Must match the rounds authored in the voice script.
voice_script.hook_line must Opening line, with hook_tone marker.
voice_script.rounds[].tone_marker must Square-bracket tone per round, e.g. [warm], [curious].
voice_script.synthesis_speech cat 5 Required for collection-based styles.
voice_script.closing_line must With closing_tone.
screen_frames[].widget must Named widget ID known to the frontend (e.g. photo_display, counter).
screen_frames[].widget_params must Widget-specific params. Type-checked at load.
screen_frames[].animation must Named animation ID (e.g. sparkle_highlight, fade_in).
screen_frames[].sfx_cue must Named SFX ID, resolved at runtime to an audio file.
screen_frames[].trigger must When the frame fires — round start, correct answer, closing.
celebration_frame optional A final screen on completion. Most playbook designs should have one.
collection_catalog cat 5 Correct items and distractors, with IDs and match hints.
collection_count cat 5 How many items before synthesis.
photo_features cat 5 Hints for vision-based validation of captured photos.

6. Notes

  1. The design studio in this repository is one reference implementation of Band II. It is useful for reading, not sacred. Any layer that solves the two challenges is a valid replacement.
  2. The playbook, not this document, is the source of truth. If this document contradicts the playbook, trust the playbook and update this document.
  3. The recipe contract in section 5 is maintained by the runtime team. If it changes, re-verify before using this as a checklist.
  4. The runtime is out of scope. An intern's job ends when a recipe passes the contract validator.
  5. Ship small. A working recipe that validates is worth more than a perfect design that does not.
