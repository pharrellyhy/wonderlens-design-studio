Build to the playbook, not to the reference.

General
Notes
  1. The pipeline has three bands: upstream data, authoring, and runtime. Data flows downstream only.
  2. The design studio in this repo is one reference implementation of the authoring band. You may use it, fork it, replace it, or write your own from scratch.
  3. Whatever you build, it must read the upstream YAMLs — do not re-invent IB themes or tier scaffolding inside an LLM prompt.
  4. Whatever you build, it must emit recipes the runtime loader accepts — YAML frontmatter, structured screen frames, tone markers, asset IDs.
  5. The playbook is authoritative. If code and playbook disagree, update the code.
  6. Ship small. A working recipe that runs in the frontend is worth more than a perfect design that doesn't load.

§ 02

Two challenges

Fig. 02
Implementation constraints
Challenge A · Between Band I & Band II

Consume the YAMLs. Do not re-invent.

Band I YAML output → your authoring layer

The upstream scripts exist so IB themes and tier scaffolding are deterministic. Any authoring layer that re-guesses them inside an LLM prompt throws that determinism away.

Your implementation must read entity_ib_map.yaml and tier_guidance.yaml as structured inputs, cite the exact theme and key concept assigned, and let the rubric verify the output matches.

  • Assigned ib_theme and ib_key_concept should be deterministic, not sampled
  • Tier scaffolding should not drift run-to-run for the same entity
  • concepts_earned should be pre-computed, not LLM-guessed
  • If your layer can't cite the source YAML for a given design, you've lost the game upstream
Challenge B · Between Band II & Band III

Emit a valid recipe. First try.

your authoring layer → refs/backend/recipe_loader.py

The runtime has a strict Pydantic schema. Any authoring layer that emits prose dialogue and relies on a second LLM pass to turn it into widgets, SFX cues, and tone markers is building on sand.

Your implementation should produce a recipe that recipe_loader.py accepts on the first try, with all asset IDs already resolved. No bridge script. No Gemini call. No prayer.

  • YAML frontmatter with activity_type, metadata, ib_theme, concepts_earned
  • Structured screen_frames with widget, widget_params, animation, trigger, sfx_cue
  • Tone markers — [warm], [excited] — on every voice line
  • celebration_frame where the playbook says one belongs
  • Category 5: collection_catalog (correct + distractors), collection_count, photo_features
§ 03

Five labs

Fig. 03
~Half a day

Five hands-on stations. Do them in order — each consumes the previous one's output. By the end of Lab V you will have built a complete game from scratch against the playbook, validated it against the runtime loader, and know exactly where to extend it next.

LAB · 01

Generate inputs

Upstream data is deterministic. Start there.
Open
scripts/entity_list_generator.py, ib_theme_batch_generator.py, exploration_tier_generator.py
Run
All three in sequence.
Inspect
Pick three entities from entities.csv. Trace them through both output YAMLs. Do the IB theme and tier scaffolding make sense?
Ask yourself
If your authoring layer could read these files directly, what would it stop guessing?
LAB · 02

Read the playbook

The source of truth. Read it once, end to end.
Open
docs/game_design_playbook.md
Focus
The 10D rubric, the 6 experience pillars, the 12 game styles, the phase structure (hook → transition → rounds → synthesis → closing), tone markers in square brackets.
Inspect
The gold-standard examples (if present). What makes them good? Where does the rubric catch weak designs?
Ask yourself
If you were scoring a design without looking at the code, which rubric dimensions would be hardest to grade?
LAB · 03

Read the runtime schema

The target format. Strict, unambiguous, unforgiving.
Open
refs/backend/schemas/recipe.py, refs/backend/schemas/visual_composition.py
Exercise
Walk every class. List every required field. Note the cat1 / cat5 split. Find every field that references an asset ID (SFX, animation, widget).
Ask yourself
Which fields can be generated directly by an LLM, and which need deterministic sources from Band I?
LAB · 04

Inspect a reference game

See what "good" looks like on both ends.
Open
refs/backend/games/polka_dot_patrol.md (or any reference game)
Exercise
Read the frontmatter slowly. Map each field back to the playbook (what informs it) and to the runtime schema (what consumes it). Note which fields are deterministic and which are authored.
Ask yourself
Of everything in this frontmatter, how much could be filled in mechanically from Band I data alone? How much requires real authoring judgment?
LAB · 05 · CAPSTONE

Build a complete game

From new entity to loadable recipe. The whole arc.
Pick
A new entity that isn't yet in entities.csv. Something specific and visual.
Prepare
Run the Band I scripts on it (or do the equivalent by hand). Produce its IB assignment and tier scaffolding.
Author
Build the design. Use the reference implementation in this repo, or write your own from scratch. Follow the playbook. Pick one pillar, one game style, one tier.
Emit
A recipe that refs/backend/recipe_loader.py accepts on the first try. No post-processing, no bridge script.
Validate
Load it, start the FastAPI server, confirm the recipe appears at /game/{activity_type}.
Extend
Once it loads cleanly, add one round, swap one SFX cue, change the celebration frame. Confirm each change still loads.
§ 04

Recipe reference

Table 01
What a valid recipe contains
Table 01 · verified against refs/backend/schemas/recipe.py & visual_composition.py Use as a checklist for Challenge B.
Field Required What it is · where it comes from
activity_type must Stable identifier the runtime uses as a lookup key. Derived from entity + game style.
metadata.ib_theme must Read deterministically from entity_ib_map.yaml. Do not re-invent in the prompt.
metadata.ib_key_concept must Same source. Specific, not a list of candidates.
metadata.concepts_earned must Pre-computed from the rubric + playbook, not guessed at export time.
metadata.tier must T0 / T1 / T2. Paired with tier_guidance.yaml on the way in.
metadata.round_count must Integer. Must match the voice_script rounds actually authored.
voice_script.hook_line must Opening line. Carries a hook_tone marker.
voice_script.rounds[].tone_marker must Square-bracket tone per round — [warm], [excited], [curious].
voice_script.synthesis_speech cat 5 Required for collection-based styles (comparison chart, naming story).
voice_script.closing_line must With closing_tone.
screen_frames[].widget must Named widget ID — photo_display, counter, badge, etc. Must exist in the frontend widget registry.
screen_frames[].widget_params must Params specific to that widget. Type-checked at load.
screen_frames[].animation must Named animation ID — sparkle_highlight, fade_in, etc.
screen_frames[].sfx_cue must Named SFX ID — wonder_chime, etc. Resolved at runtime to an audio file.
screen_frames[].trigger must When the frame fires — on round start, on correct answer, on closing, etc.
celebration_frame optional A final screen frame on completion. Playbook says most designs should have one.
collection_catalog cat 5 Correct items + distractors, with IDs and match hints.
collection_count cat 5 How many items before synthesis fires.
photo_features cat 5 Hints for vision-based validation of captured photos.
